## How the Supabase integration works

- **Client init** (`src/storage.py:7`): a single `Client` created at module load
  time (not per-call) using `SUPABASE_URL` + `SUPABASE_SERVICE_KEY` — the
  `service_role` key, which bypasses RLS.
- **Text/metadata write** (`src/storage.py:12-18`, `save_moment`): a plain
  `insert` via the Data API (PostgREST), not a raw Postgres connection —
  matches the "Enable Data API" step from setup. `id`/`created_at` are
  generated by the database, not passed from code.
- **Voice write** (`src/storage.py:21-26`, `upload_audio`): uploads to the
  `voice-notes` Storage bucket under a random `{uuid4()}.ogg` name, then
  `get_public_url()` returns the URL that `save_moment` stores as
  `audio_url`. Two round trips to Supabase per voice message.

## How the Telegram polling loop works

- `Application.builder().token(...)` authorizes with `TELEGRAM_BOT_TOKEN`.
- `run_polling()` repeatedly calls `getUpdates` (long-polling, ~30s hold),
  tracking an offset so messages aren't re-delivered. It calls
  `deleteWebhook` and `getMe` on startup — confirms we're in the polling
  mode chosen deliberately in `CLAUDE.md` (no public endpoint needed).
- Two handlers: text (excluding commands) and voice. Voice messages are
  downloaded from Telegram before being forwarded to Supabase.
- Both handlers reply `"Zapisano."` as user-visible confirmation.

## Environment variables

`TELEGRAM_BOT_TOKEN`, `SUPABASE_URL`, `SUPABASE_SERVICE_KEY` — all read via
`os.environ["KEY"]` (not `.get()`), so a missing value crashes on startup
rather than failing silently. Reasonable trade-off for a personal tool:
fail loud, don't silently drop data.

## Retrospective

**What went well**
- Clean separation of concerns (`config.py` / `storage.py` / `bot.py`) —
  secrets, data access, and bot logic don't bleed into each other.
- The architecture decisions from `CLAUDE.md` were followed exactly:
  polling over webhook, Supabase over Google Drive, raw audio preserved
  alongside text.
- `run_bot.ps1`'s duplicate-run guard and logging show attention to local
  reliability, which wasn't explicitly specified — good initiative beyond
  the spec.

**What needs attention**
- The public-bucket / RLS / region items above are gaps between what was
  *decided* and what was *built*. Worth a short follow-up pass
  (arguably a v0.1.1, not a new milestone) before capturing real content
  about the kids.
- The 2-week usage validation hasn't started yet — v0.1 is code-complete
  but not yet proven against its own success criterion.

**For v0.2 and beyond**
- Before starting v0.2 (transcription + tagging), fix the bucket privacy
  gap — retrofitting it later means re-uploading or re-signing every
  moment captured in the meantime.
- This is also a good moment to actually run the 2-week capture habit
  test now, in parallel with any v0.1.1 fixes, rather than waiting for
  "perfect" before starting to use it.
